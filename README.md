# 네이버 스마트플레이스 자동화 구축 프로젝트

운영 개선 및 조사 예정 사항: [TODO.md](TODO.md)

사장님 알림 수신 번호는 프로젝트 루트의 `.env`에서 `OWNER_PHONE=번호`로 관리합니다.
번호는 하이픈 없이 입력하고, 변경 후 백엔드와 모니터를 재시작하면 적용됩니다.
미설정 시 사장님 알림은 발송하지 않습니다. `.env`는 Git 추적 대상에서 제외됩니다.

장시간 실행 진단 로그는 모니터 시작 시와 **15분 간격**으로 자동 수집합니다.
저장 위치는 `IZI_LOG_DIR/diagnostics`이며, 미설정 시 `backend/logs/diagnostics`입니다.
파일명은 `diagnostics_YYYY-MM-DD.jsonl`이고 30일·전체 50MiB로 제한합니다.
PC 메모리·CPU, Chrome/ChromeDriver/Python/Electron의 PID·개수·메모리·CPU,
디버그 Chrome의 창 수·탭 수와 시작·종료·드라이버 복구 이벤트를 기록합니다.
진단 이벤트는 15분 주기와 별도로 기록하며, 시스템 조회 중에는 최대 수십 초 지연될 수 있습니다.
현재 모니터 PID 이외의 프로세스는 `all_pc_unclassified`로 표시하므로 다른 앱도 포함될 수 있습니다.
프로세스 CPU는 두 샘플 간 평균이며 PC 전체 처리 용량 대비 %입니다. 최초 값이나 접근 불가 값은 `null`입니다.
로그 수집은 예약 처리와 분리되어 있으며, 조회 실패 시 오류 종류만 기록하고 다음 주기에 재시도합니다.
URL·예약 내용·입금 내역은 진단 로그에 저장하지 않습니다.
`stop_izi_auto.bat` 종료 시 전체 서비스 종료 완료도 기록하며, 강제 종료·PC 멈춤 시에는 완료 기록이 없을 수 있습니다.
이 기능은 장애 원인을 조사하기 위한 것으로, PC 멈춤 문제 자체를 해결한 것은 아닙니다.

## 피아노 스튜디오 예약·입금·문자 발송 자동화 시스템

> 네이버 스마트플레이스 예약 접수부터 입금 확인, 예약 확정, 안내 문자 발송까지
> 운영자가 손으로 하던 반복 업무를 자동화한 내부 운영 시스템입니다.
> 2025년 12월 실제 스튜디오에 도입 후 운영중에 있습니다.

---

### 🔍 프로젝트 배경

피아노 스튜디오는 네이버 스마트플레이스로 연습실 예약을 받고 있었고, 예약이 들어올 때마다 아래 과정을 모두 직접 처리했습니다.

1. 예약 확인
2. 입금 계좌 안내 문자 발송
3. 계좌 입금 내역 확인
4. 예약 확정 처리
5. 확정 안내 문자 발송

예약은 새벽에도 실시간으로 들어오기 때문에 운영자가 항상 대응해야 했고, 처리 누락이나 실수가 생기기 쉬웠습니다.
과정이 일정한 패턴으로 반복된다는 점에서 코드로 풀 수 있는 문제라고 보고 프로젝트를 시작했습니다.

---

### 🎯 목표

- 반복되는 예약 관리 업무 자동화
- 운영자의 상시 개입 최소화
- 예약 상태에 따라 다음 작업이 자동으로 이어지는 구조 설계
- 실제 운영 환경에서 24시간 안정적으로 동작하는 시스템 구축

### 🧩 주요 기능

#### 1. 예약 모니터링 (Selenium)

- 네이버 예약 관리 페이지를 주기적으로 스크랩해 신규·변경·취소 예약 감지
- 신규 예약은 `신청` 상태만 처리 대상으로 걸러 DB에 저장
- 예약 변경 감지 시 DB 반영, 화면에 변경 배지 표시, 쿠폰 사용분 환불 처리
- 접수 후 **40분** 안에 입금이 확인되지 않은 예약은 자동 취소
- 동일 시간대 예약 충돌 확인 및 처리

#### 2. 입금 내역 자동 확인

- 팝빌(Popbill) 계좌조회 API로 거래 내역을 주기적으로 동기화
- 입금자명과 예약자명을 자동 매칭해 예약 확정
- 그룹 예약은 전원이 확정된 경우에만 거래를 확정 처리하고, 나머지는 수동 확인 로그로 남김

#### 3. 문자·알림톡 발송 자동화

- 예약 접수 시 입금 계좌 안내, 입금 확인 시 확정 안내 문자 자동 발송 (NCP SENS)
- 예약 요청사항이 있으면 운영자에게 알림 발송
- 쿠폰 잔여 시간 알림톡, 쿠폰 사용 내역 문자 (Windows 작업 스케줄러로 주기 실행)
- 상황별 문자 템플릿 관리, 수동 문자 발송 탭

#### 4. 쿠폰(선불) 고객 관리

- 선불 쿠폰 고객 등록, 사용 내역·잔여 시간·유효기간 관리
- 쿠폰 고객 예약은 입금 단계 없이 쿠폰 차감 후 바로 확정
- 쿠폰 수입/국산 피아노 구분, 비고란, 상세 이력 조회

#### 5. 관리자 대시보드 (React + Electron)

- 예약 / 입금 / 쿠폰 / 문자 탭으로 구성된 데스크톱 앱
- 자동화 ON/OFF 토글, 방 비밀번호 설정, 입시 기간 운영 시간 설정

#### 6. 운영 편의

- `run_izi_auto.bat` 한 번으로 백엔드·디버그 크롬·모니터·프론트·Electron 순차 실행
- 모니터 콘솔 출력을 날짜별 로그 파일로 저장하고, 에러 줄은 별도 파일로 모음 (30일 보관)
- 로그 폴더를 클라우드 동기화 폴더로 지정하면 원격에서 상태 확인 가능

### 🏗 설계

#### 예약 상태 중심 설계

`신청 → 입금대기 → 확정` (쿠폰 고객은 `신청 → 확정`) 흐름을 상태(State) 기준으로 설계해, 상태가 바뀔 때마다 다음 작업(문자 발송, 확정 클릭, 자동 취소 등)이 이어서 실행되도록 구성했습니다.

#### 백엔드 구조

```
backend/pianos/
├── scraper/        # 네이버 예약 페이지 스크랩 (Selenium)
├── automation/
│   ├── monitor.py          # 메인 루프: 예약 감지 → 처리 → 입금 확인
│   ├── account_sync.py     # 팝빌 계좌 내역 동기화
│   ├── payment_matcher.py  # 입금자명 ↔ 예약자명 매칭
│   ├── conflict_checker.py # 예약 충돌 처리
│   ├── coupon_manager.py   # 쿠폰 차감·환불
│   ├── sms_sender.py / alimtalk_sender.py
│   └── log_tee.py          # 콘솔 출력 → 날짜별 로그 파일
└── management/commands/    # 작업 스케줄러용 알림 발송 명령
```

#### 프론트엔드 구조

- Layout(Header / TabBar / Content) 구조 고정
- 포맷팅·상태 변환 로직은 utils로 분리
- Pagination, Toast 등 공통 UI는 재사용 컴포넌트로 관리
- API 호출은 도메인별 모듈(`components/api`)로 분리

#### 💰 입금 매칭

<a id="ts-1"></a>
<details>
<summary><b>1. 입금자명이 예약자명과 달라 확정 실패</b></summary>
<br>

- **문제**: 입금이 들어와도 이름이 정확히 일치하지 않아 예약이 확정되지 않음
- **원인**
  - 반각/전각 문자, 공백, 특수문자 차이
  - 은행이 바이트 제한에 맞춰 입금자명을 잘라서 보냄 (특히 긴 외국인 이름)
  - 입금자명에 이름 외 문자가 붙어서 들어옴
- **해결**
  - 문자열 정규화 로직을 추가하고, 정규화한 입금자명을 DB에 따로 저장
  - `정확 일치 → 포함 관계 → 잘림 대응` 순서로 매칭 규칙을 단계화
  - 잘린 이름은 입금자명이 4글자 이상이고 예약자명이 그것으로 시작할 때, 길이 비율 또는 첫 단어 온전 포함 여부로 판단
  - 붙여 쓴 외국인 이름도 처리 (예: `zhaoruiping` ↔ `ZHAO`)
  - 매칭 로직을 공용 함수 `name_matches()`로 추출해 입금 매칭과 충돌 처리가 같은 기준을 쓰도록 통일

</details>

<a id="ts-2"></a>
<details>
<summary><b>2. 그룹 예약 일부만 확정돼도 거래 종료</b></summary>
<br>

- **문제**: 한 번의 입금으로 여러 예약을 결제했을 때, 일부만 확정돼도 나머지 예약이 누락됨
- **원인**: 하나라도 확정되면 거래 전체를 `확정완료`로 닫음
- **해결**: 묶인 예약이 모두 확정됐을 때만 거래를 닫고, 아니면 `확정전`으로 유지하며 수동 확인 로그를 남김

</details>

#### 🎟 예약·쿠폰 처리

<a id="ts-3"></a>
<details>
<summary><b>3. 확정 클릭 실패해도 쿠폰 차감</b></summary>
<br>

- **문제**: 네이버에서는 확정이 안 됐는데 쿠폰은 차감되고 DB는 확정 상태가 됨
- **원인**: 확정 버튼 클릭 결과를 확인하지 않고 다음 단계로 진행
- **해결**: 클릭 결과(반환값)가 성공일 때만 쿠폰 차감·DB 확정을 하도록 수정

</details>

<a id="ts-4"></a>
<details>
<summary><b>4. 처리 중 들어온 신규 예약 누락</b></summary>
<br>

- **문제**: 한 예약을 처리하는 동안 들어온 새 예약이 감지되지 않음
- **원인**: 주기 시작 시점에 읽은 목록만 기준으로 처리
- **해결**: 처리 도중에도 예약 목록을 다시 탐색하고, 처리 대상은 `신청` 상태로 한정

</details>

<a id="ts-5"></a>
<details>
<summary><b>5. 예약 변경 시 에러·쿠폰 환불 누락</b></summary>
<br>

- **문제**: 고객이 예약 시간을 바꾸면 에러가 나거나 쿠폰 사용분이 환불되지 않음
- **원인**: 변경을 "기존 예약 + 신규 예약"으로 인식해 서로 충돌
- **해결**: 변경 이벤트를 따로 감지해 DB에 반영하고, 화면에 변경 배지를 표시하며, 쿠폰 환불 로직을 보완

</details>

<a id="ts-6"></a>
<details>
<summary><b>6. 쿠폰 만료 상태 불일치</b></summary>
<br>

- **문제**: 유효기간을 연장해도 `만료`로 남거나, 만료 시점이 하루씩 어긋남
- **원인**: 상태를 만료로 바꾸기만 하고 되돌리지 않았고, 날짜를 UTC 기준으로 계산
- **해결**: 모델 `save()` 시점에 `timezone.localdate()` 기준으로 `활성/만료`를 항상 재계산하고, 모니터 시작 시 전체 쿠폰 상태를 갱신

</details>

</details>

<a id="ts-9"></a>
<details>
<summary><b>9. cmd 창 클릭 시 모니터 멈춤</b></summary>
<br>

- **문제**: 운영자가 모니터 창을 클릭하면 자동화 전체가 멈춤
- **원인**: Windows 콘솔의 "빠른 편집 모드"가 켜져 있으면 클릭 시 선택 상태가 되어 `print()`가 블로킹됨
- **해결**: 모니터 시작 시 Win32 API(`SetConsoleMode`)로 해당 창의 빠른 편집 모드를 끔

</details>

<a id="ts-10"></a>
<details>
<summary><b>10. 원격에서 장애 원인 파악 불가</b></summary>
<br>

- **문제**: 운영 PC가 스튜디오에 있어 오류가 나도 콘솔 내용을 볼 수 없음
- **해결**
  - 콘솔 출력은 그대로 두고 날짜별 로그 파일에도 기록 (`log_tee.py`)
  - 에러 줄과 Traceback은 별도 파일로 모음
  - 로그 폴더를 클라우드 동기화 폴더로 지정해 원격에서 확인

</details>
